# NightWatch 賣點與簡報講稿

## 一句話介紹

NightWatch 是服務的 AI 值班員：把分散的觀測集中到 Guard Room，由 Watcher 查證異常、參考歷史經驗，留下有證據的調查報告。

## 五個核心賣點

1. **用監控室的概念，理解整個系統。** Monitor 是各處的觀測點；Guard Room 集中服務狀態、關聯與歷史快照；Watcher 就像坐在監控室的值班員，透過工具追查異常。可搭配第 2 頁概念圖。
2. **接入有彈性，調查流程可重用。** Python 可用 `@monitor(MonitorConfig(...))` 標記要觀測的函式，記錄執行、耗時、日誌與例外。事件可經 JSONL 或 HTTP 傳送；其他系統可以透過轉接層轉成 `nightwatch.log.v1`，送到 `POST /api/logs`，再設定 `monitor_id` 與服務節點的對應。接入新的系統後，Watcher 可沿用相同的 Guard Room 調查工具。可搭配第 5 頁核心賣點的條列講。
3. **從發現異常，接續到查證與報告。** Watcher 能查看服務圖、比較歷史快照、查看節點細節與搜尋日誌，根據取回的證據整理結論。持續的新異常可觸發調查，也能手動開始。可搭配第 4、5 頁。
4. **舊報告能成為下一次調查的起點。** Agent 讀取舊報告、比對相似問題，再用當前觀測確認過去的原因與處理經驗是否適用。產品價值是累積可重用的調查經驗。目前保留 5 筆紀錄，後續擴充 KB。可搭配第 5 頁。
5. **判斷依據與成本都看得見。** 工具呼叫、回傳證據、調查報告及模型對話可以回看；用量列呈現 token、快取和工具呼叫統計。報告也能交代證據不足、限制與下一步。可搭配第 4 頁實際截圖。

## Guard Room 與 decorator：可直接講的版本

「我們把這套系統想成一間 Guard Room。Monitor 是放在服務各處的觀測點，Watcher 則是坐在監控室裡的 AI 值班員。

接入方式很有彈性。Python 服務可以透過 decorator 標記要觀測的函式；其他系統則可以用轉接層，把事件轉成共同的 protocol。Guard Room 依照設定，把這些訊號對應成服務圖，Watcher 就能使用同一套工具查詢和調查。

這樣的價值是，接入不同應用時，可以調整觀測來源與服務映射，重用後面的調查流程。購物網站就是我們目前展示的整合範例。」

技術名稱：decorator 是 Monitor 端的 `@monitor(MonitorConfig(...))`；`nightwatch.log.v1` 是送入 Guard Room 的事件格式。兩者分別負責收集與交換觀測資料。

## 收尾與未來方向

## 說法依據與目前邊界

- 接入方式、事件格式、服務映射與核心流程：依 `README.zh-TW.md` 的「運作方式」及「接入你的系統」。這是專案自訂的接入方式，不宣稱為業界通用標準。
- 工作台、歷史快照、調查紀錄與用量顯示：依 `console/README.md`，以及 2026-09-12 保存的真實 Console 截圖。
- 歷史報告比對已實作、目前保留 5 筆：依使用者確認；2026-09-12 的 Demo 實際觀察到 Agent 讀取歷史案例並比較本次差異。
- OpenMetrics 與 KB 是未來工作；其他系統仍需事件轉接與服務映射設定，不宣稱任意系統零設定接入。
- 目前主軸是監測、調查與報告；不宣稱通用自動修復，也未測得節省工時或診斷準確率。

## 第 5 頁：合併後的核心賣點

「這套設計有三個重點。第一是接入彈性，Python 用 decorator，其他系統可以透過共同事件格式與轉接層接入。第二是 Agent 用工具查服務圖、快照和日誌，讓報告留下證據。第三是讀取歷史報告，找相似問題，但會用目前的觀測重新查證，確認以前的原因是否適用。」

此頁合併原本的 Protocol、工具調查與歷史報告三頁；Demo 維持第 4 頁，專案儀表板為第 6 頁，Future Work 為第 7 頁。
