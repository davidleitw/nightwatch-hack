# control 06:模型排查:唯讀工具、證據、預算、程序門檻

## 為什麼要有這段
這是 demo 的主角:模型拿著唯讀工具自己找根因。Go 這邊要把工具做穩、把證據記好、把預算管住,模型才有東西可查、人才有東西可審。

## 目標
- 模型客戶端走契約指定的介面,支援工具呼叫與用量回報;啟動時探測模型可不可用,不可用就走離線路徑;金鑰只從環境變數來,任何輸出都不能露出金鑰;單次請求有逾時,連續失敗要記事件並以 unresolved 結案。
- 七個唯讀工具照契約的參數範圍與回傳形狀,參數先驗證再查,超出範圍回一句錯誤給模型;回傳超過大小上限要截斷並標示。歷史從釘住集合取、節點詳情補最慢與最錯的 span、trace 攤成一條路徑並標出錯被誰吃掉、log 聚合成 pattern、指標樣板帶基線與差值、健康檢查打 manifest 的 URL。
- 每次工具結果存成一筆有編號的證據掛在事故上,模型引用只能用這些編號。
- 靜態前綴每輪 byte-identical(不含任何時間、事故 id、回合 id),送固定的 cache key,讓 prompt cache 命中;開場給偵測簡報與節點表;每輪只追加不改舊訊息,並附上剩餘預算。每次工具呼叫與結果都寫進 journal,事故進入 investigating。
- 預算:20 次呼叫、900 秒、40 萬 token,任一用完就要求交報告,再不交就以 budget_exhausted 結案。交報告前沒讀過至少一次節點歷史與一次 trace 不算結論。
- 報告解析成契約的結構,壞 JSON 給模型重交一次;結論寫進 read model,節點的評估跟著更新;inconclusive 以 unresolved 結案。這段停在 investigating,稽核是下一段;對話模式先回不可用。

## 怎麼算做完
- 假 stack + 真模型(金鑰只給這個程序):就緒的 model 項 ok;注入 catalog 卡、偵測後事件流依序出現工具開始、觀察記錄、結論;4 到 8 次呼叫內給出根因 catalog,第二輪起用量裡有 cached token。
- 用錯的金鑰再起一次:model 項 failed、事故走離線路徑 unresolved。
- 回報不能貼金鑰或含金鑰的錯誤訊息。

## 測試
只寫契約邊界與主線:工具參數的邊界值接受與拒絕;靜態前綴兩次產生相同且不含時間與 id;trace 攤平對一棵手寫 span 樹(含錯被吃掉的例子);報告解析對範例成功、對多了雜訊的字串失敗、inconclusive 被認出。

## 不做什麼
稽核、提案、批准、動作、驗證、報告端點、對話模式。

## 接線點
接 4 的前半:假 stack + 真模型 + dev-server,前端 04 的活動流在偵測後 5 到 30 秒出現模型的「我要查什麼」與工具結果摘要,結論後固定摘要列出現根因節點;畫面上沒有就先看事件流原文有沒有那幾種事件。這段不跟真店面接,等接 4 整段好了在全 compose 上做。
