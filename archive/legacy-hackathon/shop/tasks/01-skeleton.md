# 店面 01:一個執行檔、八個服務的共同骨架,外面調得了旋鈕、量測送得出去

## 為什麼要有這段
之後每個服務都長在這個骨架上。control 注入故障與修復靠的是這裡的設定端點,偵測靠的是這裡送出去的量測;骨架不對,後面每一段都要回頭改。

## 目標
- 一個執行檔、八個子命令對應八個服務,各自起一個 HTTP 服務,收到終止訊號能優雅關閉。
- 每個服務都有健康、就緒、執行期設定三組共用端點;設定可以從外面推進來,推進來的是合併不是取代,重複推同樣內容沒有副作用。
- 每個服務有自己的出廠旋鈕表,可以用環境變數覆寫;旋鈕變了,服務內部要立刻知道並反應(之後漏水要靠這個停下來)。
- trace、metric、log 三種遙測從同一個地方初始化,沒設收集端點時也照常跑;健康與就緒檢查不產生 trace。
- 每個 span 與一個固定的 gauge 都帶著「現在是哪個設定版本」,讓 control 對得上注入的時間點。
- 一個共用的 HTTP client,服務之間互叫時 trace 會接起來。

## 契約在哪
- `../contracts/SHOP-INTERNAL.md` §1(共用端點、合併語意)、§2(出廠旋鈕表)、§8(環境變數)
- `../contracts/METRICS.md` §2.1(span 規則)、§2.2(`shop.config.revision` 那列)、§2.4(log 欄位)

## 怎麼算做完
- `go build -o shop ./cmd/shop` 後任一子命令起得來;`bun ../contracts/check-shop.ts http://127.0.0.1:<port> <服務名>` 對 catalog 與 payment 都全綠。
- 推一份新版本的設定,stdout 出現一行「設定已套用」的 log;再推一次同樣內容,沒有新 log。
- 打健康端點不產生 span,打設定端點會。
- `CGO_ENABLED=0 GOOS=linux GOARCH=arm64` 交叉編譯過。

## 測試
只寫契約邊界與主線。一定要有:旋鈕的合併與冪等;設定變更能被訂閱到;健康端點不產生 span。

## 不做什麼
任何業務端點、postgres、Dockerfile、compose。

## 接線點
做完就是「接 0」的店面端:`check-shop.ts` 對真店面與 `../stubs/fake-stack.ts` 的假店面要過同一支。
